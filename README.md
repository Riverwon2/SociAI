# SociAI — 30분 교환소

이동에 제약이 있는 1인 가구가 당일 필요한 무료·비의료 생활지원을 한 번만 요청하면, 요청을 안전한 태스크로 나누고 적합한 이웃을 순서대로 섭외해 30분 이내의 매칭 결과를 만드는 운영 에이전트다.

이 프로젝트의 핵심은 후보를 추천하는 데서 끝나지 않고, 후보의 거절이나 무응답을 관찰해 사전 승인된 범위 안에서 다음 행동까지 실행하는 것이다.

## 제품 원칙

- 요청자는 최초 제출 이후 최종 결과까지 추가 질문을 받지 않는다.
- 후보의 수락·거절·무응답은 시스템이 관찰하는 응답 이벤트다.
- 위험한 태스크만 제외하고 안전한 태스크는 계속 진행한다.
- 모든 후보와 허용된 대안을 소진하면 `unmatched`를 반환한다.
- 데모에는 가상 인물, 지역, 연락처와 응답 이력만 사용한다.

지원하는 최종 상태는 다음과 같다.

- `fully_matched`
- `partially_matched`
- `safety_excluded`
- `unmatched`

## MVP 범위

### 구현 대상

- 필수 선택 사항과 자연어 설명을 한 번에 받는 `InitialRequest`
- 실제 OpenAI API 또는 공식 SDK를 사용한 요청 해석과 태스크 분해
- 태스크별 결정론적 안전 판정과 정보 충분성 검사
- 지역, 가용 시간, 거리, 경험, 신뢰도 기반 후보 필터링과 랭킹
- 결정론적 후보 응답 시뮬레이터와 가상 시계
- 거절·무응답 후 최대 3명까지 자동 재섭외
- 안전한 태스크의 부분 성공을 보존하는 결과 집계
- 정규화 이벤트 화면과 별도의 raw 도구 이벤트 화면
- 세 대표 시나리오의 라이브 데모와 재현 가능한 테스트

### 제외 대상

- 유료 요청, 실제 결제와 외부 정산
- 실제 메시징과 연락처 교환
- 실제 지도 제공자 연동
- 실제 신원 확인과 기관 배차
- 의료행위, 현금 대리, 아동 단독 돌봄의 일반 이웃 매칭
- 시간 크레딧, 후기, 공개 성공 사례의 실제 운영

제외 기능을 화면에 표현할 때는 `simulation`으로 명확히 표시한다. Replay 데이터를 라이브 OpenAI raw 실행으로 표현하지 않는다.

## 최초 입력

`InitialRequest`는 다음 정보를 한 번에 받는다.

| 항목 | 규칙 |
| --- | --- |
| 도움 내용 | 자연어, 필수 |
| 희망 시간 | 당일 시간 범위, 필수 |
| 활동 지역 | 대략적인 지역, 필수 |
| 최대 활동 시간 | 30분 이하, 필수 |
| 시간 조정 | 사전 허용 여부 |
| 부분 완료 | 사전 허용 여부 |
| 범위 축소 | 사전 허용 여부 |
| 비용 | `none`으로 고정 |
| 결제 방식 | `not_applicable`로 고정 |
| 추가 사항 | 접근성, 물품 무게, 실내 출입 여부 등, 선택 |

필수 값이 유효하지 않거나 무료·비의료·30분 범위를 벗어나면 중간 질문 없이 안전한 최종 결과를 반환한다. 정확한 주소와 연락처는 매칭 확정 전에 후보에게 전달하지 않는다.

## 실행 파이프라인

```text
InitialRequest
  │
  ├─ 1. 경계 입력 검증
  ├─ 2. OpenAI 요청 해석·태스크 분해
  ├─ 3. 태스크별 결정론적 안전 판정
  ├─ 4. 태스크별 정보 충분성 검사
  ├─ 5. 후보 필터링·랭킹
  ├─ 6. 최고 순위 후보에게 섭외
  ├─ 7. 결정론적 응답 이벤트 관찰
  ├─ 8. 실패 원인에 따른 계획 갱신
  ├─ 9. 매칭 확정과 태스크 결과 집계
  └─ 10. 요청 최종 결과 생성
```

OpenAI는 해석, 계획·재계획, 사용자 안내 문구를 담당한다. 안전 정책, 정보 충분성, 점수, 타이머, 상태 전이, 후보 응답은 결정론적 코드가 담당한다.

후보 점수는 다음 공식을 사용하고 각 구성 요소를 UI에 표시한다.

```text
총점 = 가용성 40% + 거리 25% + 관련 경험 20% + 신뢰도 15%
```

같은 입력과 seed는 같은 후보 순서를 만든다. 동점은 `candidateId` 오름차순으로 처리한다. 후보당 가상 10분을 기다리며 최대 3명까지만 시도한다.

실패할 때는 한 번에 하나의 변수만 변경한다.

1. 다음 후보
2. 사전 허용된 시간 조정
3. 사전 허용된 범위 축소

## 프로젝트 구조와 소유권

```text
SociAI/
├─ apps/
│  ├─ server/                    # 1번: AI·오케스트레이션
│  └─ web/                       # 3번: 프론트엔드·데모
├─ packages/
│  ├─ contracts/                # 3번: 공용 Zod 계약
│  ├─ decisions/                # 2번: 안전·충분성·랭킹·정책
│  ├─ simulator/                # 2번: 시나리오·가상 시계·합성 데이터
│  └─ event-stream/             # 3번: 이벤트 계약·전송 유틸
└─ tests/e2e/                   # 3번 주도: 대표 시나리오 검증
```

| 인원 | 역할 | 주요 책임 |
| --- | --- | --- |
| 1번 | AI·오케스트레이션 | OpenAI 연동, 실행 계획, 상태 관리, 재계획, 결과 집계, 서버 이벤트 발행 |
| 2번 | 결정·검증 | 안전 정책, 정보 충분성, 후보 랭킹, 시뮬레이터, 가상 시계, 단위 테스트 |
| 3번 | 통합·프론트엔드 | 공용 계약, 이벤트 전송 유틸, UI, E2E, 라이브 데모 |

의존 방향은 단방향으로 유지한다.

```text
apps/server  ──→ contracts, decisions, simulator, event-stream
apps/web     ──→ contracts
decisions    ──→ contracts
simulator    ──→ contracts
event-stream ──→ contracts
```

`packages/*`는 `apps/*`를 import하지 않는다. `decisions`, `simulator`, `event-stream`은 서로 직접 의존하지 않고 서버 오케스트레이터가 조합한다.

## 공용 계약

`packages/contracts`를 TypeScript 타입과 런타임 검증의 유일한 원본으로 사용한다. Zod 스키마에서 정적 타입을 파생한다.

먼저 확정할 계약은 다음과 같다.

- `InitialRequest`
- `Task`
- `SafetyDecision`
- `SufficiencyDecision`
- `Candidate`
- `AgentEvent`
- `RawToolEvent`
- `FinalResult`

모든 관련 레코드는 `runId`, `requestId`, 선택적 `taskId`, 단조 증가하는 `sequence`, `schemaVersion`을 일관되게 사용한다. 도구 호출과 결과는 같은 `toolCallId`로 연결한다.

계약은 세 명이 함께 승인하며, 계약 예제와 계약 테스트도 같은 변경에서 갱신한다.

## 이벤트와 관측성

두 이벤트 스트림은 분리한다.

### `AgentEvent`

주 화면에서 사용하는 정규화된 이벤트다.

```text
request.created
plan.created
task.created
safety.checked
candidates.ranked
outreach.sent
neighbor.replied / outreach.timed_out
plan.updated
match.confirmed / task.blocked
tool.failed
request.completed
```

모든 `plan.updated`는 `revision`, `trigger`, `observation`, `previousAction`, `nextAction`, `policyApplied`, `userInputRequired: false`를 포함한다. 실패 후 다음 행동보다 먼저 발행한다.

### `RawToolEvent`

심사위원용 두 번째 화면에서 사용하는 실제 OpenAI SDK 이벤트다. Provider payload 전체를 `raw`에 그대로 보존하고 실행 메타데이터는 `raw` 밖에 둔다. 가짜 raw 로그를 만들지 않는다.

서버는 런타임 이벤트를 발행하고, `packages/event-stream`은 공용 계약에 맞는 검증·전송 유틸과 raw 보존 규칙을 제공한다. UI는 시각이 아니라 `sequence`로 이벤트를 정렬하며 알 수 없는 이벤트도 안전하게 표시한다.

## 대표 데모 시나리오

| 시나리오 | 흐름 | 예상 결과 |
| --- | --- | --- |
| 생필품 수령 | 첫 후보가 수락 | `fully_matched` |
| 분리배출 | 첫 후보 거절 → 두 번째 후보 10분 무응답 → 계획 갱신 → 세 번째 후보 수락 | `fully_matched` |
| 문서 전달과 약 복용 보조 | 문서 전달은 진행하고 의료 가능성이 있는 약 복용 보조만 차단 | 전체 `partially_matched` |

세 시나리오는 동일한 계약을 사용하는 가상 입력, 후보 목록, 응답 순서, 예상 이벤트 순서와 최종 결과 fixture를 공유한다.

## 실제 실행과 simulation 경계

실제로 동작해야 하는 범위:

- 입력 검증
- OpenAI 요청 해석과 태스크 분해
- 도구 호출과 결과 수신
- 안전·랭킹·타이머 코드
- 거절·타임아웃 후 재계획
- 두 이벤트 스트림의 실시간 전송
- 최종 결과 집계

Simulation으로 제공하는 범위:

- 요청자와 이웃 프로필
- 후보 응답과 메시지 전달
- 가상 시계
- 채팅, 지도, 크레딧과 후기 상태

## 병렬 개발 순서

1. 공용 계약, 이벤트 이름, ID와 `sequence` 규칙을 확정한다.
2. 1번은 typed stub으로 오케스트레이션을, 2번은 순수 결정 함수와 시뮬레이터를, 3번은 계약-valid fixture로 UI를 병렬 구현한다.
3. 시나리오 1을 처음부터 화면까지 수직 통합한다.
4. 거절·타임아웃이 있는 시나리오 2를 연결한다.
5. 태스크별 안전 차단과 부분 성공이 있는 시나리오 3을 연결한다.
6. 전체 테스트와 라이브 데모 리허설을 진행한다.

공용 계약과 설정 파일을 수정하기 전에는 팀에 알린다. 다른 담당자의 영역을 직접 다시 구현하지 않고 계약을 통해 연결한다.

## 완료 기준

- 실제 OpenAI 호출이 핵심 실행 경로에 있다.
- 최초 제출 후 최종 결과까지 요청자에게 추가 입력을 요구하지 않는다.
- 세 대표 시나리오가 라이브로 동작한다.
- 거절·타임아웃 후 `plan.updated`가 다음 행동보다 먼저 발생한다.
- 위험 태스크가 안전 태스크의 성공을 취소하지 않는다.
- 후보 점수 네 구성 요소가 화면에 표시된다.
- `AgentEvent`와 `RawToolEvent`가 분리되어 있다.
- raw provider payload가 변경되지 않는다.
- 모든 데모 데이터와 기능의 simulation 여부가 명확히 표시된다.
- 같은 seed가 같은 정규화 이벤트와 결과를 만든다.
- Replay와 live 실행이 명확히 구분된다.

구현 및 협업 규칙은 저장소의 규칙 문서를 따른다.
