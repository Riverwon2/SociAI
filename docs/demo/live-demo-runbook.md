# 30분 교환소 라이브 데모 런북

## 1. 데모에서 증명할 것

- 요청자는 최초 제출 후 최종 결과까지 추가 질문을 받지 않는다.
- OpenAI는 요청 해석과 계획을 담당하고, 안전·점수·타이머·후보 응답은 결정론적 코드가 담당한다.
- 후보의 거절이나 무응답을 관찰한 뒤 `plan.updated`를 먼저 남기고 다음 후보에게 이동한다.
- 위험한 작업만 제외하고 안전한 작업의 성공은 보존한다.
- 주 화면의 `AgentEvent`와 두 번째 화면의 실제 `RawToolEvent`는 분리되어 있다.

## 2. 실제 실행과 simulation 경계

| 영역                            | 데모 모드                             |
| ------------------------------- | ------------------------------------- |
| 최초 입력 검증                  | 실제 코드                             |
| OpenAI 해석·태스크 분해         | live 서버 연결 후 실제 OpenAI         |
| 안전·정보 충분성·후보 랭킹      | 결정론적 코드                         |
| 이웃 프로필·연락·응답·매칭 확정 | simulation                            |
| fixture 화면 검증               | replay                                |
| OpenAI raw 화면                 | live에서 받은 실제 SDK payload만 표시 |

replay에서는 가짜 raw payload를 만들지 않는다. live 연결을 사용할 수 없으면 replay임을 설명하고 raw 화면을 실제 실행이라고 소개하지 않는다.

## 3. 시작 전 체크리스트

- [ ] `OPENAI_API_KEY`와 서버의 모델 설정이 준비되어 있다.
- [ ] 서버 health 확인이 통과한다.
- [ ] `POST /api/runs`가 `202 Accepted`와 실행별 두 스트림 URL을 반환한다.
- [ ] 정규화 SSE가 `agent_event`, raw SSE가 `raw_tool_event`로 전달된다.
- [ ] 두 스트림의 SSE `id`와 payload `sequence`가 일치하고 각각 독립적으로 증가한다.
- [ ] 최초·새로고침 연결의 `afterSequence`와 일시 단절의 `Last-Event-ID` 복구가 동작한다.
- [ ] `pnpm verify`가 통과한다.
- [ ] `pnpm test:e2e`가 통과한다.
- [ ] 주 화면과 raw 화면을 서로 다른 창 또는 화면에 열었다.
- [ ] 입력 데이터가 모두 합성 정보인지 확인했다.

일시 단절은 동일한 `EventSource`의 기본 재연결을 사용하고, 화면 새로고침은 session 체크포인트의 스트림별 마지막 연속 `sequence`를 `afterSequence`로 전달한다. 두 경우 모두 서버가 그 값보다 큰 이벤트만 순서대로 재전송하는지 확인한다.

## 4. 화면 준비

1. 주 화면 `/`을 열고 **Raw 이벤트 화면** 버튼으로 두 번째 화면을 연다.
2. live가 준비되면 실행 방식을 **Live 연결**로 선택한다.
3. 두 화면에서 같은 `runId`가 보이는지 확인한다.
4. raw 화면에 `LIVE`가 표시되는지 확인한다.
5. replay라면 `REPLAY`와 “raw 로그를 만들지 않습니다” 안내가 보이는지 확인한다.

## 5. 대표 시나리오 순서

### 시나리오 1 — 첫 후보 수락

1. **첫 이웃이 바로 수락** 요청을 제출한다.
2. 안전 확인, 정보 확인과 후보 점수 네 항목을 짚는다.
3. 첫 후보 수락과 `match.confirmed`를 확인한다.
4. 최종 `fully_matched`를 확인한다.

예상 핵심 순서:

```text
request.created → plan.created → task.created → safety.checked
→ sufficiency.checked → candidates.ranked → outreach.sent
→ neighbor.replied → match.confirmed → request.completed
```

### 시나리오 2 — 거절, 무응답, 세 번째 수락

1. **거절과 무응답 뒤 재섭외** 요청을 제출한다.
2. 첫 후보 거절 뒤 `plan.updated`가 다음 `outreach.sent`보다 먼저인지 확인한다.
3. 두 번째 후보의 가상 10분 무응답 뒤에도 같은 순서를 확인한다.
4. 세 번째 후보 수락과 최종 `fully_matched`를 확인한다.

발표 문장:

> 요청자에게 다시 묻지 않고, 관찰한 실패 원인에 따라 허용된 다음 후보로 계획을 갱신했습니다.

### 시나리오 3 — 혼합 위험 부분 성공

1. **위험한 일만 안전하게 제외** 요청을 제출한다.
2. 문서 전달과 약 복용 보조가 별도 task로 분해되는지 확인한다.
3. 약 복용 보조의 `task.blocked`와 안전 안내를 확인한다.
4. 문서 전달의 후보 탐색과 매칭이 계속되는지 확인한다.
5. 전체 `partially_matched`와 task별 `matched`/`safety_excluded`를 확인한다.

발표 문장:

> 위험한 작업 하나가 전체 요청을 취소하지 않도록, 안전한 문서 전달의 성공을 그대로 보존했습니다.

## 6. Raw 두 번째 화면 확인

- metadata와 provider payload가 별도 영역에 있다.
- call과 result가 같은 `toolCallId`로 묶인다.
- payload는 pretty-print만 하고 필드 이름이나 값을 바꾸지 않는다.
- 호출 묶음이 200개를 넘으면 화면에는 최근 200개만 표시되며, 수신 버퍼의 payload는 유지된다.
- `waiting_for_result`가 오래 지속되면 서버와 네트워크 상태를 확인한다.
- 실제 개인정보가 포함되면 데모를 중단한다. raw는 사후에 가릴 수 없기 때문이다.

## 7. 장애 대응

| 상황                | 처리                                                                         |
| ------------------- | ---------------------------------------------------------------------------- |
| OpenAI 호출 실패    | 실제 오류 이벤트와 안전한 최종 결과를 보여주고 완료된 task가 보존됐는지 확인 |
| 구조화 출력 실패    | 서버의 1회 재시도 뒤 안전 종료를 설명                                        |
| SSE 일시 단절       | 화면의 reconnecting 상태와 마지막 연속 sequence 이후 복구 확인               |
| 후보 없음·모두 거절 | 허용된 fallback 또는 `unmatched` 확인                                        |
| 브라우저 새로고침   | 동일 run의 마지막 sequence 다음부터 재개 확인                                |
| live 서버 미준비    | fixture replay로 전환하고 live raw 실행이라고 설명하지 않음                  |

## 8. 리허설 기록

| 항목                        | 시나리오 1      | 시나리오 2      | 시나리오 3          |
| --------------------------- | --------------- | --------------- | ------------------- |
| 시작부터 완료까지 실제 시간 |                 |                 |                     |
| 이벤트 누락·중복            |                 |                 |                     |
| `plan.updated` 선행 순서    | 해당 없음       |                 |                     |
| raw call/result 상관관계    |                 |                 |                     |
| 최종 결과                   | `fully_matched` | `fully_matched` | `partially_matched` |
| 남은 위험                   |                 |                 |                     |

최소 10회 반복 실행한 결과와 미실행 검증을 최종 작업 보고서에 기록한다.

새로고침 복구 검증에서는 실행 생성 API가 다시 호출되지 않는지, 주 화면의 기존 정규화 타임라인이 복원되는지, 정규화/raw 스트림이 각각 자신의 마지막 연속 `sequence` 다음부터 요청되는지 함께 확인한다. raw payload 자체는 브라우저 저장소에 남기지 않는다.
